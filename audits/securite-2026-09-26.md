## Résumé exécutif

Aucun constat CRITIQUE ni ÉLEVÉ. **3 MOYEN** et **13 FAIBLE**. Ce qu'ils ont en commun : ce que
l'application promet à la fermeture d'un coffre, à l'effacement ou à la conversion **ne suit pas tous les
chemins** — l'éditeur garde le clair (V1), l'index de recherche garde l'ancien texte (K1), et sous
Android 7.0-8.1 le coffre à code ne tient pas contre un téléphone saisi (K4).

Trois actions prioritaires : 1) l'éditeur oublie le clair quand le coffre se ferme (V1) ;
2) FTS5 en `secure-delete` + une purge unique de l'existant (K1, P3) ; 3) coffre à code sous l'API 28 :
refuser ou dire sa limite, pages légales comprises (K4).

### Modèle de menace

Notes Markdown chiffrées, aucune permission réseau (« 100 % local »). Base SQLCipher sous KEK scellée
Keystore. Coffres : phrase secrète (Argon2id 64 Mio) ou code 4-6 chiffres (Argon2id 32 Mio + scellé
Keystore `setUnlockedDeviceRequired`, effacement au 5e code faux). Verrou d'app : PIN (Argon2id + HMAC
Keystore) + biométrie classe 3. Mode panique. `allowBackup=false`. Attaquants : **A** téléphone
déverrouillé en main (prêt, fouille — `NotesTechApplication.kt:99-103`) ; **B** app malveillante sans
root ; **C** copie du stockage / téléphone saisi, avec pour certains constats du code sous l'UID de l'app
(root, forensique AFU) ; **D** contenu hostile.

### V1 — MOYEN — note de coffre lisible et copiable après la fermeture du coffre (CWE-613)

- `ui/editor/NoteEditorViewModel.kt:819-822` met le clair dans l'état (`content = TextFieldValue(claire.content)`).
- `NotesTechApplication.kt:108-110` : `onStop` → `vaults.lockAll()` ; `security/vault/VaultSessions.kt:177-182`
  n'efface **que les clés**. L'éditeur n'observe pas `unlockedFolderIds` (lu seulement par `HomeRoute`,
  `FoldersDrawerViewModel`, `NoteExporter`) ; `lockedVault` n'est posé qu'au chargement (`:805`) ou sur un
  échec d'écriture (`:952`).
- Au retour, même ViewModel : `NoteEditorScreen.kt:580` faux, `:631` affiche `state.content` ; copie par le
  menu (`NoteEditorViewModel.kt:591-596`) ou par la barre de sélection, sans session.
- **Attaquant** A, sans verrou d'app (défaut) ou revenu dans le délai. **Gain** : titre et corps de la (des)
  note(s) de coffre dont l'éditeur est dans la pile ; aucune autre voie sans le secret. Même défaut par
  l'auto-verrouillage d'inactivité (15 min), app au premier plan.
- **Bornes** : notes ouvertes au départ seulement ; processus vivant ; un verrou d'app « immédiat » ferme le chemin.
- **Confiance** HAUTE (vérifié par l'orchestrateur, `fichier:ligne` relus).
- **Correction** : à toute fermeture de session (arrière-plan, inactivité, manuelle, panique), l'éditeur
  jette titre et corps et passe à l'état verrouillé ; la copie refuse sans session vivante.
  **Coût** : au retour, le secret est redemandé ; l'enregistrement en attente (≤ 500 ms) doit partir **avant**
  la fermeture, sinon il échoue en « coffre refermé ».

### K1 — MOYEN — ancien clair d'une note mise au coffre dans l'index FTS5 (CWE-212)

- `security/vault/FolderVaultService.kt:569-589` (`encryptAllNotesInFolder`) → `lockNote` (`UPDATE`) →
  déclencheur `notes_au` (`data/local/UnmanagedSchema.kt:117-119`) : `'delete'` avec les **anciennes
  valeurs en clair** (`masked()` ne masque que si `encrypted_content` était déjà posé). FTS5 n'écrit qu'un
  marqueur ; termes et positions (`detail=full`, table `:79-88`) restent dans `notes_fts_data` jusqu'à une
  fusion. Aucune purge dans le code (`optimize`, `merge`, `secure-delete` : absents — vérifié).
- Même résidu par `reprotectPlaintextNotes` (`:713-725`) et `NotesRepository.moveToFolder` vers un coffre.
- **Survit à l'auto-effacement et à la suppression du coffre** (`notes_ad` avec valeurs masquées n'ajoute ni
  ne retire rien). Contredit `UnmanagedSchema.kt:90-92` (« une note verrouillée n'expose rien à l'index ») et
  l'écran « définitivement perdues ».
- `note_links` : les gestes de masse ne suppriment pas les liens sortants (l'édition le fait,
  `NotesRepository.kt:343`) ; **mais** ils partent avec la note (`ON DELETE CASCADE`) : cette partie ne
  survit pas à l'effacement, et ne vaudrait seule que FAIBLE.
- **Attaquant** C avec la clé de la base (code sous l'UID, root). **Gain** : texte normalisé mais
  reconstructible (positions) des notes converties, sans le secret du coffre.
- **Correction** : option FTS5 `secure-delete` + une purge unique de l'existant (`optimize`) ; **pas de
  `rebuild`** (il relirait les colonnes brutes et indexerait titres format 1 et étiquettes des notes
  verrouillées) ; gestes de masse alignés sur l'édition pour les liens. **Coût** : suppressions plus lentes ;
  table illisible par FTS5 < 3.42 (retour à Flutter impossible de toute façon). À prouver par un test qui
  cherche le mot dans `notes_fts_data` après conversion.

### K4 — MOYEN — coffre à code sous Android 7.0-8.1 (CWE-307)

- `security/vault/AndroidVaultKeystore.kt:272-283` : `setUserAuthenticationRequired(false)`, et
  `setUnlockedDeviceRequired(true)` seulement `if (SDK_INT >= P)`. `minSdk = 24` (`app/build.gradle.kts:82`) ;
  le mode code est proposé sans condition (`ui/vault/VaultSheets.kt:207-220`).
- Chemin : clé de la base (K3) → colonnes du coffre (`FolderDao.kt:112-119`) → un appel Keystore ouvre le
  scellé (`FolderVaultService.kt:360`) → Argon2id t=2 32 Mio par code, étiquette GCM comme oracle, ≤ 1,11
  million de codes. Le compteur de 5 essais n'est jamais traversé.
- Présenté comme une protection : « Device-bound security (Keystore) » (`values/strings.xml:297`),
  `raw/privacy.md:14`, `raw/terms.md:25` — sans réserve pour Android < 9. Même recette que la 2.0.9 (parité).
- **Attaquant** C (saisie AFU + code sous l'UID). **Gain** : tout le contenu des coffres à code.
- **Correction** : sous l'API 28, ne plus proposer le code (phrase secrète seule) ou dire sa limite à l'écran
  **et** dans les pages légales ; prévenir les coffres à code existants sur ces appareils. **Coût** : perte
  du mode code sur Android 7-8.1 ; écart assumé avec la 2.0.9.

### P1 — FAIBLE — clair hérité de Flutter jamais purgé (CWE-459)

- `share_plus` 10.1.4 (2.0.0 à 2.0.9) copie **chaque fichier partagé** dans `cache/share_plus/`
  (`Share.kt:187`, `:245-252`), **avant** d'ouvrir le sélecteur (donc même partage annulé), et ne vide ce
  dossier qu'au partage suivant (`:95`). La 3.0.0 ne purge que `cache/exports` et `cache/captures`
  (`NotesTechApplication.kt:61`, `:67`) ; seule la panique vide le reste. Comme la 3.0.0 n'appelle plus
  `share_plus`, cette copie est **figée indéfiniment**.
- **Gain** pour C (copie du bac à sable AFU/root) : le dernier export 2.x en clair — s'il s'agissait du ZIP,
  toutes les notes, coffres alors ouverts compris, et des notes supprimées depuis. Accessoires (incidents
  seulement) : `<titre> [unlocked].md` à la racine, `stt_capture_*.wav`.
- **Gravité** : deux votes MOYEN, un FAIBLE (un seul fichier, choisi par l'utilisateur) → FAIBLE, le plus bas.
- **Correction** : au démarrage, plus aucun clair hérité (`share_plus/`, `.md`/`.zip` à la racine,
  `stt_capture_*.wav`), avec la définition d'`estUnArtefactSensible` et suppression vérifiée. Rend vraie la
  promesse `NoteExporter.kt:329-331`. **Coût** : aucun.

### V2 — FAIBLE — la preuve du PIN survit à l'arrière-plan (CWE-613)

`ui/applock/AppLockSettingsViewModel.kt:241` garde la preuve à l'étape NEW ; avec un délai (non défaut),
`RelockPolicy.kt:56-59` → `LOCK_LATER`, l'époque ne change pas (`AppLockManager.kt:195`) ; A revient dans
le délai et < 2 min → `replacePin` (`:296`). Gain réel seulement avec la biométrie active (le propriétaire
continue à l'empreinte, A garde un PIN durable). **Correction** : toute sortie de l'app oublie la preuve.

### K2 — FAIBLE — lien resté résolu vers une note de coffre (CWE-1230)

`encryptAllNotesInFolder` et `reprotectPlaintextNotes` n'appliquent pas `resolveIncoming`
(`NotesRepository.kt:782-788`) que l'édition et le déplacement appliquent ; `NoteLinkDao.kt:44-45` sans
filtre ; `LiensDeLaNote.kt:136-138` affiche une puce résolue, qui ouvre la feuille du coffre en le nommant.
Gain : un bit (« une note de ce titre existe ») et le coffre qui la contient ; viole la règle écrite
`NoteDao.kt:155-158`. **Correction** : mêmes règles de liens pour les gestes de masse + réparation unique
des bases existantes. Même défaut : les liens sortants de la note scellée réapparaissent dans son panneau
coffre ouvert (contredit D-024, sans fuite).

### K3 — FAIBLE — clé de la base utilisable téléphone verrouillé (CWE-922)

`security/kek/KeystoreSealedKekSource.kt:243-251` sans `setUnlockedDeviceRequired` ; la copie
`flutter_secure_storage` (clé RSA sans l'attribut) reste en repli. Le vérificateur d'impact l'a réfuté :
les coffres tiennent, les notes exposées sont celles que l'app déclare « sans protection par mot de
passe », et la clé brute est en mémoire tant que le processus vit. **Ne pas lier la clé** : elle serait
**supprimée** au retrait du verrouillage d'écran (mesuré API 34) — toute la base perdue.
**Vérification de l'orchestrateur (risque de perte, hors panel)** : la passerelle qui pose l'attribut est
dans **toutes** les versions publiées de 2.0.4 à 2.0.9 (`KeystoreBridge.kt:241-242` au tag v2.0.9). Quand
Android supprime cette clé, `load()` rend `null` (`KeystoreSealedKekSource.kt:62`), la copie Flutter rend
la clé et `promoteToPrimary` (`KekRepository.kt:156`) la rescelle sans l'attribut : **pas de perte**, à une
condition — que la copie Flutter existe encore. **Correction** : écrire le choix (KDoc « délibérément
absent », décision) ; écrire la vraie raison de garder la copie Flutter (la raison actuelle, « retour en
arrière », est caduque) ; corriger `docs/10-PASSERELLE-2.0.4.md` §5 (faux deux fois) ; ajouter le test
instrumenté « scellé de la passerelle dont la clé a disparu → copie Flutter → rescellé ».

### K5 — FAIBLE — le vérificateur du verrou d'app sert d'oracle (CWE-307)

`security/applock/AndroidAppLockKeystore.kt:27-29` (clé HMAC sans attribut ni limite) ; vérificateur en
préférences ; Argon2id précalculable, un HMAC Keystore par candidat. Le gain « PIN de coffre » est
**réfuté** (le scellé d'un coffre à code s'ouvre avant le code, et exige un appareil déverrouillé). Reste :
la valeur du PIN, utile seulement si elle est aussi le code de l'écran. **Correction** : documenter la
limite (D-023) ; ne pas lier la clé (même problème de suppression que K3 : l'utilisateur serait enfermé).

### E1 — FAIBLE — navigation pilotée par un intent externe (CWE-926)

`MainActivity` exportée ; Navigation 2.9.8 honore `android-support-nav:controller:deepLinkIds` /
`deepLinkExtras` de n'importe quel appelant (bytecode). Sans `noteId`,
`NoteEditorViewModel.kt:190` (`checkNotNull`) tue le processus ; B choisit aussi l'écran d'ouverture.
Aucune lecture, écriture ni ouverture de coffre ; le vérificateur d'impact le juge informatif.
**Correction** : retirer les extras `android-support-nav:controller:*` de l'intent avant `setContent`
(Navigation elle-même peut lever sur un intent malformé : corriger la ligne 190 ne suffit pas).

### E2 — FAIBLE — reverrouillage repoussé indéfiniment (CWE-613)

`RelockPolicy.kt:71-72` : tout `onStart` consomme l'échéance ; `:57` la réarme à chaque `onStop` ; aucun
plafond. Une app qui relance `MainActivity` avant chaque échéance l'entretient ; exige de pouvoir lancer
en arrière-plan (Android 7-9, ou superposition accordée) — non mesuré, d'où un vote « faux ». Contredit
l'écran « verrouiller 5 min après avoir quitté l'app ». **Correction** : l'échéance part du dernier départ
réel et n'est pas consommée par un retour que l'utilisateur n'a pas initié.

### F4 — FAIBLE — le clavier apprend le contenu des coffres (CWE-524)

`NoteEditorScreen.kt:630-641`, `:738-763` et la feuille de lien (`FeuilleDAutocompletion.kt:153-165`) :
`TextField` sans demande d'apprentissage désactivé ; **Compose 1.11.3 n'expose même pas
`IME_FLAG_NO_PERSONALIZED_LEARNING`** (absent du bytecode). Gain : fragments non attribuables, survivant à la
panique. **Correction** : poser le drapeau par un intercepteur de saisie (`InterceptPlatformTextInput`) sur
ces trois champs ; ce n'est qu'une demande au clavier.

### F1 — FAIBLE — la barre de sélection copie une note de coffre sans protection (CWE-359)

`NoteEditorScreen.kt:630-641` (corps), `:738-763` (titre) : `TextField` Material3 ordinaires ; aucun
`LocalClipboard` ni `LocalTextToolbar` redéfini ; Compose foundation 1.11.3 écrit
`ClipData.newPlainText` sans `IS_SENSITIVE`. Le jumeau protégé est le menu Copier
(`NoteEditorViewModel.kt:590-597` → `SensitiveClipboard`, marquage API 33+, effacement 60 s). Le
vérificateur d'impact l'abaisse à FAIBLE : l'extrait est choisi par le propriétaire, le flux dominant
(copier pour coller ailleurs) laisse le même clair par les deux chemins ; le différentiel réel est le
couper/coller interne et le marquage. Défenses : aucune garde. **Retenu 2/2.**

### F2 — FAIBLE — les feuilles de secret naissent sans `FLAG_SECURE` (CWE-696)

`VaultSheets.kt:388`, `:655`, `AppLockSettings.kt:251` : `ModalBottomSheet` sans `properties`, donc
`SecureFlagPolicy.Inherit`, lu **dans le constructeur** de `ModalBottomSheetDialogWrapper` (bytecode de
Material3 1.4.0), pendant la composition qui exécute aussi `SecureWindowGuard` — dont la demande
n'atteint la fenêtre de l'activité qu'à une recomposition suivante. Réglage « Masquer dans les apps
récentes » désactivé : pavé du code, phrase secrète et PIN d'app tapés dans une fenêtre capturable,
alors que chaque garde promet le drapeau « même si l'utilisateur l'a désactivé ». Attaquant B avec
capture consentie. **Retenu (rapide)** ; **mesuré ensuite** : le test de la correction lit la fenêtre
d'une feuille ordinaire au-dessus d'une activité non protégée — elle naît sans le drapeau.

### P2 — FAIBLE — le clair hérité part en dernier dans la panique (CWE-696)

`PanicService.kt:452` : `CACHE_PURGE` au rang 12, derrière `DB_WIPE`, le modèle de dictée, 530 Mo de
modèles hérités et les préférences ; les étapes de clair (6, 7) ne visaient que `exports/` et
`captures/`. Le clair de la 3.0.0 part bien tôt ; celui laissé par 2.x (P1) attendait la fin, et une
interruption (extinction, batterie) le laissait sans reprise. **Retenu (rapide).** Second volet, non
corrigé (§9) : une panique interrompue entre la clé et la base mène à l'écran d'échec de démarrage, qui
dit les notes intactes et n'offre que « Réessayer ».

### P3 — FAIBLE — ce qui est supprimé reste dans l'index et les pages libres (CWE-226)

`UnmanagedSchema.kt:110-115` (`notes_ad`) : marqueur `'delete'` seulement ; ni `optimize`, ni `merge`, ni
option `secure-delete` ; pas de `PRAGMA secure_delete`. Cinq gestes ordinaires (corbeille vidée,
suppression définitive, purge à 30 jours, dossier supprimé, coffre à code effacé) laissent termes et
positions à qui ouvre la base avec sa clé — contre « effacée définitivement » et « irréversible ».
Sous-point confirmé : l'effacement d'un coffre à code ne vérifiait pas la disparition de sa clé Keystore
et retirait quand même son journal de reprise (`FolderVaultService.kt:835`, `:855`). **Retenu (rapide).**

### P4 — FAIBLE — la fin de panique promet plus que l'app ne peut effacer (CWE-451)

`SensitiveClipboard.kt:330` ne vide que le clip principal ; l'historique d'un clavier (Gboard, Samsung)
est hors de portée de toute app, et `IS_SENSITIVE` n'existe qu'à partir de l'API 33. L'écran affirme
pourtant « Toutes les données ont été effacées » après « aucune récupération forensique possible ».
Le défaut est la formulation, pas le code. **Retenu (rapide).**

## 4. Ce que le panel a réfuté ou corrigé

- **K3** : gravité ramenée de MOYEN à FAIBLE (impact : pas de secret à protéger, coût du correctif = perte de la base).
- **K5** : « le PIN d'app ouvre un coffre » — faux (`FolderVaultService.kt:360` ouvre le scellé avant le code).
