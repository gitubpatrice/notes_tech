# K5 — angle IMPACT — verdict : FAUX POSITIF (reçu 2026-09-26)

VERDICT : FAUX POSITIF (angle IMPACT). Mécanisme exact (clé HMAC sans authentification ni déverrouillage, `AndroidAppLockKeystore.kt:27-29` ; sel et étiquette dans les préférences, `AppLockStore.kt:148` ; étiquette = HMAC(libellé ‖ Argon2id), `AppLockPin.kt:131-146` ; temporisation dans l'app seulement, `AppLockManager.kt:212-247`) : C essaie les codes sans limite, AFU. Mais le gain annoncé n'existe pas au-delà de ce que C a déjà.

**1. Dans l'app, le code du verrou n'ouvre rien que C n'ait déjà.** Clé de la base sans contrainte (`KeystoreSealedKekSource.kt:243-251`) ; seul `setUnlockedDeviceRequired` = coffres (`AndroidVaultKeystore.kt:283`) ; C lit toute la base. `AppLockKeystore.kt:8-9` : « the database opens at start-up without any user secret ». Aucun fichier de `security/vault`, `security/kek`, `data` ne fait référence au verrou d'app ; aucun mode leurre ou de contrainte rattaché.

**2. Le gain « PIN d'un coffre » (raison de D-023, `docs/01-DECISIONS.md:640-644`) est réfuté par le code.** Un coffre à code a son propre scellé Keystore, ouvert AVANT que le code intervienne (`FolderVaultService.kt:360` `keystore.open(VaultParams.pinKeystoreAlias(folderId), ...)`, puis Argon2id(code) `:373-375`). API 28+ : scellé lié au déverrouillage (`AndroidVaultKeystore.kt:283`) : téléphone verrouillé, même le bon code n'ouvre rien. Là où le scellé s'ouvre (téléphone déverrouillé, ou API 24-27 : `minSdk = 24`, garde `:273`), C n'a pas besoin de l'oracle : il appelle `open` lui-même puis cherche hors ligne (compteur en base, `FolderVaultService.kt:256`). Coffre à phrase secrète ≥ 8 caractères (`VaultParams.kt:78`) : un code de 4-6 chiffres ne peut pas en être un.

**3. Seul gain restant : le code de l'écran, par réutilisation — une supposition.** Aucune ligne ne l'établit (commentaire `AppLockKeystore.kt:10-11`). Il faut que C ait le téléphone en main (du code sous l'UID ne saisit pas un code sur l'écran de verrouillage) et un écran verrouillé par un code numérique de 4-6 chiffres identique. Pour le public visé (téléphones sans verrouillage d'écran, `AppLockKeystore.kt:25-26`), gain nul avec certitude ; sans verrouillage d'écran, un coffre à code ne peut même pas être créé en API 28+ (`AndroidVaultKeystore.kt:348-352`). « Exploitable dans certaines configurations » : faux positif selon le critère.

**Ce qui renverserait le vote** : tenir pour acquis la réutilisation du code d'écran → au plus FAIBLE (AFU, chaîne d'exploitation complète, réutilisation ; gain = contourner la limitation matérielle des essais de l'écran de verrouillage). La mention « possiblement réutilisé pour un coffre » doit de toute façon être retirée (point 2).
