Voici les constats de l'audit, classés par sévérité, en ciblant spécifiquement les motifs architecturaux demandés.

SEVERITE: CRITIQUE
FICHIER: lib/ui/screens/note_editor_screen.dart:692
STATUT: CONFIRME
DEFAUT: Jumeau asymétrique / Faille de chiffrement : la création d'une note via un lien fantôme (backlink) dans un dossier coffre omet de chiffrer la note initiale, la persistant définitivement en clair en base.
SCENARIO: 1. Ouvrir une note dans un coffre. 2. Taper `[[Secret]]` et appuyer sur le lien fantôme pour créer la note. 3. La nouvelle note est créée avec `encryptedContent == null`. 4. L'éditeur s'ouvre, `isLocked` est évalué à faux, `_wasLocked` reste faux. 5. L'utilisateur tape son texte, l'auto-save persiste le contenu en clair dans la base de données au sein du coffre.
CORRECTIF: Dans `_createFromDangling` et `_insertLink`, si `_wasLocked` est vrai, chiffrer la note nouvellement créée avec `_vault.encryptNote` avant de l'ouvrir ou de la sauvegarder.

SEVERITE: MAJEUR
FICHIER: lib/ui/screens/note_editor_screen.dart:547
STATUT: CONFIRME
DEFAUT: Chemin mort / Garde sur l'affichage : la condition d'avertissement de sortie de coffre vérifie `n.encryptedContent != null`, ce qui est toujours faux car la note en mémoire (`_note`) a déjà été déchiffrée lors du `_load` et ce champ a été purgé.
SCENARIO: 1. Ouvrir une note de coffre (elle est déchiffrée en RAM, `encryptedContent` devient null). 2. Choisir "Déplacer" vers un dossier standard. 3. L'avertissement destructif (F1 v1.1.0) n'apparaît pas car la condition échoue silencieusement. 4. La note est sauvegardée en clair sans le consentement explicite de l'utilisateur.
CORRECTIF: Remplacer `n.encryptedContent != null` par `_wasLocked`.

SEVERITE: MAJEUR
FICHIER: lib/ui/screens/note_editor_screen.dart:194
STATUT: CONFIRME
DEFAUT: Repli du mauvais côté : dans `_flushFinalSave`, si le coffre se verrouille entre `isUnlocked` et `encryptNote`, l'exception est silencieusement avalée par le catch global, causant la perte définitive des modifications.
SCENARIO: 1. L'utilisateur édite une note de coffre. 2. Il quitte l'écran (déclenche `dispose` et `_flushFinalSave`). 3. Exactement au même moment, l'auto-lock du coffre s'active. 4. `isUnlocked` passe, mais `encryptNote` lève `VaultLockedException`. 5. L'exception est attrapée ligne 194, la modification est perdue et le repli de sécurité vers `vault_lost_drafts` n'est jamais exécuté.
CORRECTIF: Déplacer la logique de sauvegarde de secours (`vault_lost_drafts`) dans un bloc `catch (VaultLockedException)` spécifique autour de `encryptNote`.

SEVERITE: MAJEUR
FICHIER: lib/ui/screens/note_editor_screen.dart:301
STATUT: CONFIRME
DEFAUT: Condition de course asynchrone : la méthode `_saveNow` n'attend que la sauvegarde immédiatement en cours (`if` au lieu de `while`), ce qui provoque des UPDATE concurrents si plusieurs sauvegardes s'empilent.
SCENARIO: 1. L'utilisateur tape du texte, pause 500ms (Save 1 démarre, prend du temps). 2. Il retape, pause 500ms (Save 2 démarre et `await Save 1`). 3. Il retape, pause 500ms (Save 3 démarre et `await Save 1`). 4. Save 1 termine. Save 2 et Save 3 se réveillent exactement en même temps et lancent `_doSave` concurremment, causant une corruption ou un blocage SQLite.
CORRECTIF: Remplacer `if (pending != null)` par `while (_pendingSave != null) { await _pendingSave; }`.

SEVERITE: MINEUR
FICHIER: lib/services/export/note_export_service.dart:436
STATUT: CONFIRME
DEFAUT: La fonction `_disambiguate` ne vérifie pas si le nom généré avec suffixe existe déjà dans la map `used`, ce qui cause une collision silencieuse dans le ZIP.
SCENARIO: 1. Exporter trois notes dans le même dossier : "Note", "Note-2", et "Note". 2. La première devient `note.md`. 3. La deuxième devient `note-2.md`. 4. La troisième génère `note-2.md` car le compteur de "note" est à 2. 5. Le ZIP contient deux fichiers `note-2.md`, causant un écrasement à l'extraction chez le destinataire.
CORRECTIF: Boucler avec `while (used.containsKey(candidate.toLowerCase()))` pour incrémenter le suffixe jusqu'à trouver un nom libre, puis l'ajouter à la map `used`.

SEVERITE: MINEUR
FICHIER: lib/services/export/note_export_service.dart:418
STATUT: CONFIRME
DEFAUT: Jumeau asymétrique : la fonction `_safeFolderDirName` omet de filtrer les noms réservés Windows (`CON`, `PRN`, etc.), contrairement à son jumeau `safeFileName`.
SCENARIO: 1. L'utilisateur crée un dossier nommé "CON". 2. Il exporte ses notes en ZIP. 3. Il tente d'extraire le ZIP sous Windows. 4. L'extraction échoue car l'OS interdit la création d'un dossier portant ce nom.
CORRECTIF: Appliquer la même vérification de la constante `reserved` dans `_safeFolderDirName` que dans `safeFileName`.

*(Note sur les motifs : Les 4 motifs demandés ont tous été identifiés et documentés dans les constats ci-dessus. Aucune anomalie de type "zéroisation en RAM" n'a été détectée sur le code fourni, les chaînes Dart étant immuables et le cycle de vie du `SecureWindowService` étant correctement géré au `dispose`.)*
